# 问题管理后端详细设计 v0.2

2026-11-07；可供需规/详设评审的起稿，尚未获得业务签字。依据：项目HTML问题管理区及其JavaScript。未发现后端代码、数据库规范、共享接口定义。数据库已按用户要求采用PostgreSQL，语法按14+兼容设计，部署版本待确认。接口前缀、字段长度、文件限制及权限规则仍是本稿假设，评审结论优先。

## 1. 范围与模块责任

问题服务维护问题快照、回复/确认/转交历史、参与者、附件关联及可靠事件。评审房间服务负责评审单、房间、批注、模型/基线和报告；用户/组织/项目授权复用平台；账号映射归系统管理；文件实体复用集团文件服务；TC适配器由集成团队确认。不要在问题库复制用户、评审房间等主数据表。

本稿API包含10项核心能力和5项依赖/待确认扩展。批量、导入/模板、AI生成虽在原型存在，未进入已承诺契约；评审若纳入本期必须补设计。关闭问题不自动等于评审审批通过，是否存在未关闭问题阻断房间结束由评审模块决策。

## 2. 状态机与操作权限（暂定）

|动作|前状态|角色|后状态|关键约束|
|---|---|---|---|---|
|CREATE|无|有房间提问权限者|DRAFT|创建人为提出人；业务来源去重|
|EDIT|DRAFT|提出人|不变|概述必填；其他业务字段可补齐|
|SUBMIT|DRAFT|提出人|PENDING_REPLY|等级、描述、处理人及关联对象完整|
|EDIT|PENDING_REPLY|当前处理人|不变|仅方案、截图|
|REPLY|PENDING_REPLY|当前处理人|REPLIED|条件校验采纳、整改、理由、意见|
|EDIT|REPLIED|提出人|不变|仅描述、方案、截图|
|CONFIRM resolved=false|REPLIED|提出人|PENDING_REPLY|退回意见必填|
|CONFIRM resolved=true|REPLIED|提出人|CLOSED|有效建议方案非空，设置closed_at|
|TRANSFER|PENDING_REPLY|当前处理人|不变|新处理人有效且有资格，不能转给本人|
|REOPEN|CLOSED|提出人或当前处理人|PENDING_REPLY|清空closed_at，保留历史结论|
|DELETE|DRAFT|提出人|DRAFT+deleted_at|逻辑删除；不可再次查询/操作|

服务端根据状态和操作者计算allowedActions。UPLOAD的用途分别受EDIT/REPLY权限限制；RETRY_SYNC需额外权限。前端隐藏按钮不是权限控制。version冲突要返回409，不能默默覆盖。

创建时将提出人与非空处理人加入participant；草稿修改处理人、提交、转交也加入新处理人且不移除旧人（这是否使未正式办理的旧草稿处理人仍可见，需业务确认）。转交不能只改handler_id，否则旧人从已办消失。查询用EXISTS而不是多表直接JOIN，避免一条问题因多条历史变成多行。

## 3. 数据结构及字段维护方式

|表|职责|要点|
|---|---|---|
|im_issue|当前快照|版本、来源、关联对象、状态、当前处理人、TC摘要|
|im_issue_action|全部业务动作和每轮回复|一次业务版本一条动作；不能覆盖旧回复；包含字段前后值|
|im_issue_participant|历史参与集合|支撑转交后已办可见，不授予跨项目权限|
|im_issue_attachment|文件元数据及绑定|TEMP→BOUND，扫描CLEAN才可绑定；回复附件关联action|
|im_issue_outbox|TC及通知可靠事件|主事务写入，后台重试；包含消费租约及去重键|
|im_issue_idempotency|请求去重及结果重放|租户+用户+请求键唯一；请求摘要含方法和路径|

完整类型、长度、索引、CHECK及注释见ddl.sql。本模块业务ID和外键使用PostgreSQL UUID，应用生成、API序列化为标准UUID字符串；外部ID仍为VARCHAR(64)。布尔字段用BOOLEAN（true/false/null），结构化载荷用JSONB，时间统一TIMESTAMPTZ(3)。租户/项目/组织/提出人从认证和房间数据推导，不接受客户端伪造。姓名、报告名、基线编号为展示快照，关联始终使用稳定ID。DDL只加本模块内外键，跨服务关系由服务校验；所有子表tenant_id必须与主表一致，外键本身不提供租户隔离。

字段维护时逐项记录：中文名称、API字段、库字段、类型/长度、是否可空、草稿/提交阶段必填、字段来源、谁在什么状态可改、是否同步TC。生成的字段字典.md可作为建模器录入底稿。数据库NULL与JSON null一致；更新请求省略字段表示不改，不支持随意用null清空，按接口约定用空字符串或空数组。

不把adopted/completed放在主表覆盖历史；从action取得最近REPLY。激活/退回后的上一轮结论只是历史，不能冒充当前轮次已完成。TC同步载荷的结论需带动作ID和业务版本。

### PostgreSQL实现约定

- 主键UUID由应用生成，DDL不依赖扩展或数据库UUID生成函数；外部人员/项目等ID保留字符串。API中的UUID字段增加format约束，业务编号仍是普通字符串。
- 时间用TIMESTAMPTZ(3)，表示绝对时间点，不保留输入的原始时区名称；连接池统一UTC，前端按Asia/Shanghai显示。写入时传带偏移的时间，不传含糊的本地时间。DEFAULT CURRENT_TIMESTAMP(3)是事务开始时间；业务更新显式写updated_at，若需要语句执行时间用statement_timestamp()，租约实时判断可用clock_timestamp()，不要依赖自动更新时间。
- 布尔值用BOOLEAN，JDBC/ORM绑定true/false而非0/1；变化快照、事件载荷及幂等响应为JSONB，hash必须根据请求的规范化结构计算，不依赖JSON键顺序或JSONB输出文本。
- 所有表/列注释采用COMMENT ON；普通索引独立CREATE INDEX。主表处理人/提出人/数据范围索引仅覆盖deleted_at IS NULL记录，并按updated_at DESC,id DESC排列，查询必须包含该谓词。唯一编号/来源约束覆盖已删除记录，避免重用；可空来源引用和TC UID使用默认唯一约束语义，允许多个NULL。
- 标识符及业务唯一键按区分大小写设计，不能沿用原MySQL默认不区分大小写的假设。业务编号若要忽略大小写，应先规定统一大小写再入库。用户文本搜索使用参数化ILIKE，转义百分号、下划线与转义符；包含查询不承诺B树加速，未来按规模评估pg_trgm，当前DDL不安装扩展。
- 参与者upsert使用INSERT ... ON CONFLICT (issue_id,user_id) DO UPDATE。幂等占位用ON CONFLICT DO NOTHING RETURNING ...，冲突后再查询已提交结果；不要直接捕获唯一键异常后在已失败事务中继续执行。查询不到结果或等待超时按可重试冲突处理。
- 列表与counts在同一个REPEATABLE READ READ ONLY事务内查询才共享一致性快照；PostgreSQL默认READ COMMITTED下，多条SELECT不会自动共享同一快照。
- outbox领取可用FOR UPDATE SKIP LOCKED，但必须同时约束同issue_id+destination不存在更低版本未完成事件；不能跳过被锁住的旧版本去发送新版本。领取和续租使用短事务，远端调用在事务之外，回写仍匹配lock_token。
- 迁移脚本在选定schema中执行，表名不强制写public。连接用户仅授予所需schema权限；tenant_id只是数据列，不自动产生行级隔离，应用仍须检查租户和授权。

类型语义依据PostgreSQL官方文档：[时间类型](https://www.postgresql.org/docs/14/datatype-datetime.html)、[UUID](https://www.postgresql.org/docs/14/datatype-uuid.html)、[JSON/JSONB](https://www.postgresql.org/docs/14/datatype-json.html)。14+表示本稿语法兼容基线，不代表推荐部署14；实际部署版本按集团标准确认。

## 4. 写入事务与并发

回复、确认、编辑、转交共享以下事务框架：

1. 认证及参数静态校验；取对象并检查数据权限；规范化请求计算hash。
2. 开启事务；插入幂等键。遇到已完成同键同hash直接重放；不同hash返回409；并发同键等待锁后读取结果，若超时返回可重试冲突。业务失败回滚键，不能留下永久PROCESSING。
3. SELECT主记录FOR UPDATE，检查租户、deleted_at、version、当前状态和角色；必要时重新校验资格。依赖不可用返回503，不能默认为通过。
4. 校验关联对象一致、条件必填和附件所属用户/问题/用途/扫描状态；锁定附件防止重复绑定。
5. UPDATE im_issue ... WHERE id=? AND tenant_id=? AND version=? AND deleted_at IS NULL；业务version+1，显式写updated_at/updated_by；影响0行则409。
6. 写action、upsert participant、绑定附件；需要通知/TC的动作分别写outbox；同步触发时主表置PENDING。
7. 写幂等成功响应，与业务一并commit。TC/通知实际发送在提交后异步执行。

创建初始version=1并写CREATE记录；来源键防止同一批注多次创建（包括7天请求去重期之外）。DRAFT编辑不发送TC；提交及后续编辑、回复、确认、转交、激活发送快照；DELETE仅草稿不发TC。通知针对提交、回复、退回、关闭、转交、激活，接收者ID写入事件且去重；例如回复通知提出人，转交通知新处理人。

幂等键同一租户用户内全局唯一，包含路径hash，因此不能在不同接口复用；保存期7天为建议。文件上传使用同一规则，以文件SHA256和purpose加入摘要。存储文件的远端调用不在长事务内：先上传到隔离临时区，再保存元数据及幂等结果；数据库失败的孤儿对象由清理任务回收。

## 5. TC与消息可靠性

暂定平台为主数据、单向同步。TC真实接口URL、对象类型、状态/等级/人员字段映射尚未提供；本稿不虚构可直接调用的TC接口。需TC负责人出映射表：本地ID、issue_no、TC UID、状态、等级、提出人/处理人TC账号、房间/模型关联、当前回复、版本。

业务事务内写outbox，worker按同一问题/目标的版本顺序处理；前一条失败时后续同目标事件阻塞，修复后顺序重试（防止旧转交晚到覆盖新人）。不同问题可并行。worker用locked_until/lock_token租约领取并续租，成功/失败回写必须匹配token。崩溃后允许重放；TC适配器必须支持以事件ID幂等，或通过本地问题稳定ID查找/更新TC对象，不能每次失败重新创建。

重试建议指数退避1分钟起，上限30分钟，最多10次自动重试后进入人工处理；次数与SLA待集成评审。手动retry重新置失败事件PENDING并清零本轮attempts，保留原事件ID与快照。只在最新业务版本被成功同步后将主表标记SUCCESS，旧版本成功不得覆盖新版本的PENDING/FAILED；同步元数据回写不修改业务version/updated_at。通知单独目标独立重试，避免TC失败阻断通知。详细投递日志复用平台日志，敏感内容脱敏。

## 6. 附件与数据安全

上传要求问题已存在。截图、回复附件不存数据库BLOB。只允许白名单实际文件类型，限制大小与数量；扫描完成后方可绑定/下载。TEMP文件仅上传人可查，24小时过期；BOUND回复附件保留不可覆盖。截图编辑可以移除当前关联，但物理对象至少保留到审计保留期，历史changes记录附件ID；具体保留期与历史查看接口需要集团规则确认。

接口返回文件元数据，不暴露object_key。下载接口验证附件确属该问题且CLEAN/BOUND，返回短签名URL并记审计；集团若不允许URL临时可转发，应替换为认证下载代理。列表和计数不得泄露无权项目，日志不得记录令牌/签名URL。所有字段按白名单更新，客户端不能直接改status、raiserId、tenantId、tcSyncStatus。

## 7. 查询和接口文档写法

接口文档必须写：场景、方法/路径、鉴权、路径/查询/请求字段及必填、条件校验、状态变化、事务/幂等、成功示例与错误码、联调责任。不能只列Java DTO属性。接口文档.md及yapi.json为同源生成，修改generate_contract.py后重新生成，避免两份口径漂移。

固定排序updated_at DESC,id DESC；处理记录issue_version ASC。keyword为编号或标题包含查询，基线/房间编号包含查询；escape通配符。包含查询无法假定普通B树索引高效，数据量明确后EXPLAIN并评估前缀匹配/检索服务。counts复用相同筛选，忽略bucket和分页，在同一只读一致性快照计算，避免列表和数量不一致。

统一响应示例：

```json
{"code":"OK","message":"处理成功","traceId":"trace-demo","data":{"id":"5b591019-f732-4f43-8121-a4313e1e3787","version":3,"status":"REPLIED","tcSyncStatus":"PENDING"}}
```

回复示例（HTTP POST /api/v1/issues/{issueId}/replies；同时传Authorization与Idempotency-Key）：

```json
{"version":2,"adopted":true,"modificationCompleted":true,"handlingOpinion":"ACCEPTABLE","body":"已完成整改，请确认。","attachmentIds":[]}
```

转交示例：`{"version":2,"targetHandlerId":"user-102","reason":"由结构专业继续处理"}`。

|HTTP|业务码示例|处理|
|---|---|---|
|400|INVALID_ARGUMENT|字段类型、长度、枚举错误|
|401|UNAUTHENTICATED|重新登录|
|403|ISSUE_OPERATION_FORBIDDEN|无操作角色/权限|
|404|ISSUE_NOT_FOUND|不存在、删除或数据范围不可见|
|409|ISSUE_VERSION_CONFLICT / ISSUE_STATE_CONFLICT / IDEMPOTENCY_CONFLICT|刷新或按原键重试；不可盲目覆盖|
|413/415|FILE_TOO_LARGE / FILE_TYPE_NOT_ALLOWED|更换附件|
|422|ISSUE_RULE_VIOLATION / ATTACHMENT_NOT_READY|补齐业务字段或等待扫描|
|503|DEPENDENCY_UNAVAILABLE|稍后重试；不得伪造成功|

## 8. 开发验收用例

1. 草稿→提交→回复→退回→第二轮回复→关闭→激活，验证每轮历史不丢，状态/时间/版本正确。
2. 不采纳缺理由、采纳缺整改/意见、关闭缺有效方案、退回缺意见均失败且不写历史。
3. A转给B后A已办/B待办；B再转给C后A/B仍可查历史；兼任提出人场景TODO优先。
4. 非当前处理人回复/转交、其他租户查看/下载、跨问题绑定附件均失败；列表和计数同权限。
5. 两人使用同version并发操作，只成功一次，历史/outbox不重复；同幂等键重复请求重放，异请求拒绝。
6. TC超时，本地结果保持成功，TC状态失败可见；重试不创建重复TC对象，旧版本不能覆盖新处理人。
7. 未扫描/拒绝/超大文件不能绑定；上传成功但未提交的临时文件会清理；历史回复附件不被覆盖。
8. 已提交问题删除失败；仅草稿可删除；归档后规则在需求确认后追加验收。

这些是实现后的验收目标，本次只生成设计工件，没有运行后端行为测试或TC联调。
