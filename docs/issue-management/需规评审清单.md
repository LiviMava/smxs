# 问题管理需规评审清单

基于项目《交流评审首页.html》及问题管理JS，2026-11-07。这里的“建议”用于推动会议决策，不是已批准需求。先确认业务规则，再维护建模器字段，不宜把演示代码当生产规范。

## 评审开场可直接这样说

“问题管理分工目前列了查询、详情、编辑、上传、转交五类接口，但原型还包含回复确认闭环、草稿、激活、批量、导入和TC同步。请先确认本期范围以及和评审房间的创建边界，再确认状态、权限、数据范围，避免字段维护和开发后返工。”

## 必须在需规评审结束前定下来的问题

|优先级|会上具体提问|原型依据或矛盾|本稿暂定/对设计的影响|建议确认人|
|---|---|---|---|---|
|P0|问题由批注自动产生，还是房间手动创建？谁提供创建、提交接口？批注修改/删除是否联动问题？|列表提示“问题从评审房间内创建”，但仍保留列表新建函数与旧演示数据|统一问题服务落库；房间调用创建草稿接口；批注不能直接删除已提交问题；创建去重键必须明确|评审房间负责人、业务|
|P0|本期是否包含草稿、提交、确认关闭/退回、激活、批量删除/处理、导入、模板、TC重试、AI建议？|实际原型明显超出五类分工|前五类拆成10个核心接口，另提供5个依赖/扩展接口；批量、导入、AI尚未承诺，需要补责任与估时|项目经理、业务|
|P0|“处理编辑”是修改基本信息，还是提交回复，还是提出人确认？保存是否推进状态？|详情有编辑保存、处理回复、确认操作|编辑不推进状态；回复与确认独立命令，避免一个update接口任意改status|业务、前端|
|P0|草稿究竟谁可编辑、提交、删除？|needsAction允许提出人或处理人；列表按钮按提出人；详情草稿操作按处理人|暂定仅提出人；不能直接照搬前端判断|业务|
|P0|待办、已办、全部分别是什么数据集合？原处理人转交后还能看吗？提出但尚未办理算已办吗？|doneItems按当前相关人且无待执行动作；转交弹窗明确旧处理人进已办|暂定“历史参与且无当前待办”即DONE；保留历史参与表。是否必须实际操作过需明确|业务、权限负责人|
|P0|全部是“我参与的”、房间全部、事业部全部还是集团全部？管理员如何查询？|列表ALL仅isRelated，计数却用全部数组长度|暂定授权范围内历史参与；管理员扩展暂不开放；计数与列表同条件，不能越权计数|业务、权限负责人|
|P0|提出人与处理人可以同人吗？人员离职/失权时谁接管？转交对象是否限房间成员？|原型用固定姓名选项|按用户ID；转交需有效人员及项目/房间处理权限。离职代办/管理员强制转交需单独确认，不默认为管理员任意改|业务、组织权限负责人|
|P0|不采纳时，修改完成、处理意见是否必填？采纳但未完成能提交吗？|单条表单一直显示；批量逻辑只对采纳要求完成及意见|采纳必填完成/意见；不采纳必填理由、其余两项为空；允许提交未完成回复；业务确认后固定统一规则|业务|
|P0|谁确认关闭？不采纳能否关闭？关闭是否必须建议方案？退回意见是否必填？|原型存在单条、批量校验差异|仅提出人确认；关闭需有效建议方案；退回需非空意见；不采纳关闭例外待定|业务|
|P0|关闭后谁能激活，能激活多少次？房间归档/报告签发后还能激活吗？|列表允许提出人或处理人；详情操作条件不同|暂定二者均可，保留每轮历史；归档后规则未定，是上线阻断项|业务、归档负责人|
|P0|一个问题是否关联多个模型/基线/报告/房间？关联的是哪一版本？|原型为单值；旧创建代码将review写入baseline|本稿单值稳定ID+版本/名称快照；多关联需改子表，不能混用评审单ID与基线ID|业务、数模/评审负责人|
|P0|TC和本平台哪个是问题主数据？是否双向？TC对应对象及字段是什么？|原型同步仅写死“成功”|暂定本平台主数据、单向异步；双向需补冲突裁决、回流幂等、防循环。要拿到TC UID、账号映射与状态映射|TC集成负责人|
|P0|TC失败是否阻断问题流转/房间结束？缺少TC账号映射怎么处理？|演示允许同步失败问题存在|本地事务可成功，独立FAILED/PENDING；是否允许房间完结需另定；禁止伪造成功|TC负责人、业务|
|P0|PostgreSQL部署版本、主键规范、表前缀、租户方式、统一响应和鉴权是什么？建模器是否生成表？|目录只有HTML，无后端工程/规范|已按用户要求改为PostgreSQL，语法按14+兼容设计；确认实际部署版本，避免与建模器生成表重复|架构、数字化团队|

## 应在详设冻结前确认

|事项|具体问题|本稿建议|
|---|---|---|
|字段|S/A/B/C的业务定义是什么？S是否阻断评审审批？问题编号按集团/项目/年度连续吗？是否允许断号？|等级不擅自赋予定义；编号用集团服务，禁止MAX+1；默认租户内唯一|
|可编辑性|REPLIED时提出人能改标题/等级吗？修改原描述会不会改变回复依据？|单条详情只允许描述/方案/截图；标题等级批量差异暂不扩展；记录变更前后值|
|附件|截图能替换还是追加？回复附件类型/大小/数量？数模原文件是否允许上传？|拟定单文件20MiB、每次最多10个；截图PNG/JPEG，回复增加PDF/DOCX/XLSX；不可覆盖历史回复证据|
|导入|模板有哪些字段？导入产生草稿还是待回复？一行失败全撤回还是部分成功？怎样判重？|待确认扩展；需模板版本、任务ID+行号幂等、逐行错误报告；未提供伪可用接口|
|批量|是否同状态批量？逐条权限如何校验？部分成功还是全成全败？最多多少条？|建议同状态、逐条权限/version校验，最多100条；原子性会议确定后补接口|
|通知|转交、回复、退回、关闭、激活通知谁？站内还是邮件/IM？如何去重？|拟定站内通知异步；待办必须从业务状态可重建，通知失败不回滚业务|
|统计|已办数按问题数还是操作次数？跨轮次退回怎样计整改时长？转交耗时算谁？|统计模块消费操作历史；问题列表按issue去重，统计口径另形成字典|
|安全|密级、跨事业部、房间成员移除后历史是否可见？下载、水印、导出、审计留存怎么定？|租户+项目/房间授权+参与者；失去项目权限不能因历史参与绕过；密级规则需接集团权限服务|
|AI|AI建议属于Q4吗？模型在哪里？哪些数模内容允许送入？是否必须人工确认？|本稿不实现AI接口；若立项，AI仅建议草稿，不直接回复或关闭|
|容量|一年问题量、最大房间问题数、并发、附件总量、列表P95目标？|先确定真实规模再做性能验收；列表分页20、上限100为暂定|
|记录|历史是否要求不可篡改？删除/归档/保留期限？|业务操作追加保存，普通用户无修改入口；数据库权限和归档策略另定|

## 要求会议输出的材料

1. 范围与责任矩阵：每项是否Q4、需求提出人、产品确认人、实现人、联调人。
2. 状态转移表、角色权限表、TODO/DONE/ALL样例及验收结果。
3. 字段字典（类型、必填、长度、枚举、来源、编辑阶段），据此维护建模器。
4. TC字段/状态/账号映射和失败补偿协议；评审房间、文件、人员、权限接口契约。
5. 未决问题台账：编号、结论、负责人、期限、影响接口/表，不以“后续再说”替代决策。

若“下周”以当前2026-11-07为基准：周一/二为11月9/10日，周三为11月11日，周五为11月13日。引用的原始计划若不是本周发出，应以项目经理确认日期为准。
